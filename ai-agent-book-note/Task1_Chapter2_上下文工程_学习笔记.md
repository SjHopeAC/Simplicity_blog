# Task 1：Chapter 2 上下文工程（Context Engineering）学习笔记

## 一、本章要解决的问题

上下文工程不是“把 Prompt 写长一点”，而是由 Agent 框架在**每一次模型调用之前**决定：模型这一轮能看到什么、信息以什么结构排列、哪些内容常驻、哪些内容按需加载、哪些历史需要压缩。

本章可统一成一个问题：

> 如何在 token、延迟和费用受限的条件下，为模型构造一份信息充分、结构清晰、来源可信且尽量复用缓存的输入？

从工程上看，上下文工程最终操作的是两类数据：静态前缀与动态轨迹。静态前缀主要包括系统指令和工具定义；动态轨迹由用户消息、模型回复、工具调用与工具结果不断追加而成。Prompt、Skills、状态栏和压缩看似是四种技术，实质都是在控制这两部分的内容与布局。

## 二、前置概念

### （一）Agent、模型、环境与 Harness

1. **大语言模型（LLM）**：根据本轮输入预测输出。它负责判断“下一步做什么”，但不会因为输出了一个工具调用 JSON 就自动执行真实操作。
2. **环境（Environment）**：Agent 之外的真实世界，例如文件系统、浏览器、数据库、天气服务。进入上下文的是环境的观察结果，不是环境本身。
3. **Agent Harness（运行框架）**：围绕模型工作的宿主程序。它保存消息历史、注册工具、调用模型、解析 `tool_calls`、执行工具、追加结果，并决定何时停止或继续。
4. **Agent**：在本章的工程语境下，可理解为“模型 + Harness 提供的上下文和工具能力”形成的完整任务执行系统。

四个角色的控制关系如下：

- 开发者创建 Harness，并向它注册系统指令、工具定义和工具实现。
- Harness 持有 `messages`、`tools`、运行状态和工具路由表；模型 API 只接收本轮请求。
- Harness 调用模型；模型返回文本或工具调用请求。
- 只有 Harness 会调用真实工具；工具访问环境并把结果返回 Harness。
- Harness 把模型回复和工具结果追加到历史，再次调用模型，直到模型给出最终文本或达到停止条件。

> 易混点：模型“选择工具”不等于模型“执行工具”。`tool_calls` 只是结构化请求；真实副作用发生在 Harness 调用工具实现时。

### （二）上下文、上下文窗口与轨迹

**上下文（Context）**是模型在某一次推理时实际收到的全部信息，通常包括系统指令、工具定义、用户消息、模型历史回复和工具结果。**上下文窗口（Context Window）**是模型一次最多可处理的 token 容量。**轨迹（Trajectory）**则是一次任务中观察与动作交替积累的历史。

其中 `o` 是用户消息或工具结果等观察，`a` 是模型回复或工具调用等动作，`c_t` 是截至当前的轨迹。模型下一步基于整个 `c_t` 决策，而不是只看最后一条用户消息。

> “模型 API 无状态”在本章特指 Chat Completions 式调用：上一轮内容不会凭空出现在下一轮请求里，Harness 必须保存并重新提交必要历史。某些 API 可以用服务端会话标识简化传输，但“由系统决定下一轮可见上下文”的责任并没有消失。

### （三）Token、Chat Template 与注意力

1. **Token**：模型处理文本的基本单位，不等同于一个汉字或一个英文单词。
2. **Chat Template**：把结构化的 `system/user/assistant/tool` 消息和 `tools` 描述序列化为模型训练时熟悉的 token 序列。
3. **因果注意力**：某个位置只能关注自己及之前的 token，因此在末尾追加内容不会改变前面 token 已计算的表示；改动中间内容则会影响变动点之后的计算。

这解释了两个工程结论：应保持前缀稳定；动态信息优先追加到末尾。

## 三、消息 API：上下文在代码中的最小形态

### （一）四种消息角色与工具字段

本章以 Chat Completions 风格协议为例。一条消息的最小结构是：

```python
message = {
    "role": "system | user | assistant | tool",
    "content": "消息内容"
}
```

- `system`：开发者提供的身份、规则和工作流程。
- `user`：终端用户请求；某些 Harness 也会借用这一协议角色注入框架生成的信息。
- `assistant`：模型之前的文本回复或工具调用请求。
- `tool`：工具执行结果，用 `tool_call_id` 关联对应请求。

工具定义不是第五种消息，而是请求顶层的 `tools` 字段。最小定义与调用如下：

```python
tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "查询指定城市的当前天气",
        "parameters": {
            "type": "object",
            "properties": {"city": {"type": "string"}},
            "required": ["city"]
        }
    }
}]

response = client.chat.completions.create(
    model="模型名",
    messages=messages,
    tools=tools
)
```

这里需要区分三层含义：Python 语法上，`tools` 是由字典和列表组成的对象；API 协议上，它是工具的 JSON Schema 元数据；Agent 设计上，它只告诉模型“有哪些动作及其参数”，并不包含工具的真实执行逻辑。

> 不同厂商、模型和 API 版本的角色名、思考块回传规则、工具字段会变化；学习时掌握“结构化角色 + 工具 schema + 关联 ID + 完整轨迹”这组稳定原则，不要把示例字段误认为所有 API 永久统一的规范。

### （二）Agent 核心循环的最小代码

下面只保留本章最关键的一条可执行链：

```python
import json
from openai import OpenAI

client = OpenAI()

def get_weather(city: str) -> dict:
    """真实项目中应调用天气服务；这里用固定结果说明数据流。"""
    return {"city": city, "temperature": 20, "condition": "sunny"}

tool_registry = {"get_weather": get_weather}

tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "查询指定城市的当前天气",
        "parameters": {
            "type": "object",
            "properties": {"city": {"type": "string"}},
            "required": ["city"]
        }
    }
}]

messages = [
    {"role": "system", "content": "需要实时信息时使用工具。"},
    {"role": "user", "content": "北京天气怎么样？"}
]

for _ in range(8):                       # 防止无限工具循环
    response = client.chat.completions.create(
        model="模型名", messages=messages, tools=tools
    )
    assistant_message = response.choices[0].message
    messages.append(assistant_message)   # 保留模型本轮动作

    if not assistant_message.tool_calls:
        print(assistant_message.content)
        break

    for call in assistant_message.tool_calls:
        arguments = json.loads(call.function.arguments)
        result = tool_registry[call.function.name](**arguments)
        messages.append({
            "role": "tool",
            "tool_call_id": call.id,
            "content": json.dumps(result, ensure_ascii=False)
        })
else:
    raise RuntimeError("Agent 超过最大迭代次数")
```

这段代码中的对象关系是：

- 开发者创建 `client`、`tool_registry`、`tools` 和 `messages`。
- Harness 逻辑持有并更新 `messages`；`tool_registry` 持有“工具名 → Python 函数”的映射。
- `client.chat.completions.create(...)` 把当前上下文交给模型。
- 模型创建 `assistant_message`；若其中有 `tool_calls`，每个 `call` 持有工具名、JSON 参数和唯一 `id`。
- Harness 用工具名查找函数，解析参数并真正调用；工具创建结果对象。
- Harness 创建 `tool` 消息，并把 `call.id` 写入 `tool_call_id`，使模型知道结果属于哪个调用。

### （三）完整调用链与返回点

以“北京天气怎么样”为例：

1. 用户输入请求，Harness 将其追加为 `user` 消息。
2. Harness 组合稳定的系统指令、工具定义和动态消息历史，第一次调用模型。
3. 模型判断需要实时天气，返回 `assistant.tool_calls`；此时尚未查询天气。
4. 控制权回到 Harness。Harness 先保存这条 `assistant` 消息，再按名称找到 `get_weather`。
5. Harness 执行 `get_weather(city="北京")`；真实副作用从这里开始，结果返回 Harness。
6. Harness 把结果包装为 `tool` 消息，用相同 `tool_call_id` 建立对应关系。
7. 循环回到模型调用处。第二次请求包含原系统指令、用户请求、模型的工具调用和工具结果。
8. 模型依据工具结果生成普通文本，不再返回 `tool_calls`。
9. 控制权回到 Harness；Harness 打印最终回复并 `break`，本次循环结束。

如果两个工具的参数都能由当前上下文直接确定，且二者没有数据依赖，Harness 可以并行执行；如果工具 B 的参数必须由工具 A 的结果产生，就要让模型在后续轮次再请求 B，形成串行链。

## 四、KV Cache 友好的上下文设计

### （一）KV Cache 与 Prompt Cache 的区别

**KV Cache**缓存 Transformer 各层已经算出的 Key、Value 向量，主要避免单次生成过程中反复计算历史 token 的 K、V。每生成一个新 token，仍要让新 Query 读取此前缓存，因此长上下文仍会带来显存、带宽和注意力计算成本。

**Prompt Cache**是跨 API 请求的推理服务优化：若新请求与旧请求具有相同前缀，服务端可以复用该前缀已产生的 KV Cache，减少 prefill 重算。两者都利用“前缀不变”，但层级不同：前者是一次推理内部的模型机制，后者是多次请求之间的服务机制。

> `prefill` 是模型正式生成回复前处理输入 token 的阶段；`decode` 是逐个生成新 token 的阶段。KV Cache 没有让注意力变成零成本，它省掉的是历史 K、V 投影的重复计算。

### （二）为什么前缀改动会导致缓存失效

Transformer 各层串联，位置 `k` 的表示会依赖 `1...k` 的 token。如果第 `k` 个 token 被修改，`k` 之前的缓存仍可复用，但从 `k` 开始的表示都可能变化，所以后缀必须重算。变动越靠前，重算范围越大。

因此生产设计遵循：

1. 系统指令确定后尽量不变，不要每轮把当前时间写进开头。
2. 工具定义保持固定顺序，不按使用频率动态重排。
3. 保留标准角色结构，不把所有消息拼成 `USER: ... ASSISTANT: ...` 纯文本。
4. 新信息追加到轨迹末尾，避免回头修改旧消息。
5. 不采用简单滑动窗口直接丢弃最早消息；它既破坏前缀，也可能删掉后续仍需使用的证据。

> “只追加、不改写”首先是缓存纪律；对某些把思考块与前缀签名绑定的模型，它还可能成为协议正确性要求。具体回传规则属于供应商行为，必须查看所用模型的最新文档。

## 五、提示工程：设计稳定的静态指令

### （一）系统提示词是什么

系统提示词是 Agent 的“员工手册”，负责说明身份、目标、约束、工作流程和验收标准。检验方式不是“写得像不像咒语”，而是：一个聪明的新员工读完后，是否知道何时做什么、出现异常怎么办、什么结果才算完成。

提示词应优先采用流程驱动结构，而不是堆砌大量无序规则：

```text
# 文件处理流程
1. 验证：检查路径是否存在；不存在则停止并报告
2. 分类：识别文件类型
3. 预处理：需要时备份或分块读取
4. 执行：按文件类型处理
5. 验证：检查输出完整性
```

Markdown 负责层级和可读性；XML 标签可标明信息块的语义和来源。二者是信息组织手段，不是标签越多越好。

### （二）业务规则、Few-shot 与工具描述

1. **业务规则**要写到可执行：给出适用条件、动作、例外和验证方式，不能只写“根据情况选择”。业务边界由产品负责人确定，工程师负责准确编码，不应让模型替业务制定政策。
2. **Few-shot 示例**适合难以用规则精确定义的输出，如文风、报告格式和客服语气；规则简单或模型本就擅长时，无需浪费 token。通常少量覆盖边界的高质量例子优于大量相似例子。
3. **工具描述**要说明何时使用、何时不用、参数约束、典型示例、常见错误和与其他工具的关系。函数名和 JSON Schema 只能说明“怎么传参”，无法完全说明“什么时候该调用”。

### （三）提示注入的边界

提示注入是外部网页、邮件或文档把恶意文本伪装成指令，诱导 Agent 越权行动。因为 Agent 能调用工具，风险不仅是答错，还可能变成文件写入、邮件发送或隐私泄漏。

上下文层的防御包括：用 `<external_content source="webpage">` 等结构标记来源；严格区分 `system/user/tool` 角色；对可疑内容做清洗。但这些只能降低风险，不能提供绝对安全。高风险动作仍需要权限控制、沙盒和独立确认。

> Skill 和状态栏也可能被投毒：Skill 是被主动加载的指令，状态栏又容易被模型高度信任。因此第三方 Skill 应像代码一样审查；状态栏应尽量由确定性代码生成，不能直接复制不可信外部文本。

## 六、Agent Skills：按需加载领域知识

### （一）Skill 解决什么问题

若把所有领域规则都塞进系统提示词，会浪费 token 并稀释注意力。Skill 把能力拆成可组合、可按需加载的知识包，采用**渐进式披露**：先常驻很短的目录，需要时再读取完整流程和细则。

Skill 的三层结构是：

1. **元数据目录**：常驻 `name` 与 `description`，负责发现和路由。
2. **核心流程**：任务命中后才加载完整 `SKILL.md`。
3. **细则与资产**：根据当前任务继续读取引用文档、脚本或模板。

最小 `SKILL.md`：

```markdown
---
name: pdf-review
description: 在需要检查 PDF 内容与版式时使用；纯文本文件不使用。
---

# PDF 检查流程
1. 提取文本并核对内容。
2. 将各页渲染为图片检查版式。
3. 修正后重新渲染，直到验收通过。
```

`description` 不是宣传语，而是路由条件，应同时写明正向触发条件和不适用边界。完整 Skill 还要说明角色与标准、3—5 条核心原则、禁止事项与合法例外、验证方式以及参考资料。

### （二）谁加载 Skill，正文进入哪里

- Harness 先让模型看到技能目录。
- 用户可以显式选择 Skill，或模型根据目录请求加载。
- Harness 读取 `SKILL.md`，把正文注入本轮上下文；不同 Harness 使用的消息角色和包装方式不同。
- 模型遵循正文完成任务，必要时继续按引用读取细则或调用 Skill 附带脚本。

稳定原则是“少量目录常驻、完整正文按需加载”；“Skill 正文一定属于 system 消息”并不是跨框架通用规则。Skill 第一次加载仍有 token 与计算成本，其收益是避免启动时加载全部内容，并让已建立的前缀尽量不被改写。

### （三）Skill 与工具的区别

- **工具**提供动作能力，回答“能执行什么”，例如读文件、发送请求、运行命令。
- **Skill**提供领域流程，回答“遇到某类任务时，应该按什么顺序使用哪些能力并如何验收”。
- Skill 可以指导模型组合多个工具，也可以附带脚本和模板；但模型读取一份 Skill 并不会自动产生真实副作用，副作用仍由工具执行。

## 七、Agent 状态栏：把隐式状态变成显式知识

Agent 在执行过程中还需要动态感知自身状态与任务进展。Agent 框架把这些动态信息整理成结构化摘要并注入上下文，这种机制称为 **Agent 状态栏（Agent Status Bar）**。



一个重要的实现细节是：Agent 状态栏在 API 层面实际上是作为**一条 user 角色的消息**插入到上下文末尾的——而不是修改开头的 system 消息。

Harness 是在借用 user 角色这个消息槽位，向模型注入由 Agent 框架自动生成的系统状态信息——内容并非来自真实用户，只是复用了 user 角色的消息格式来挂到上下文末尾。

### （一）为什么仅有完整历史还不够

注意力擅长从上下文中检索某条已有事实，却不擅长每轮都从大量原始记录中重新计数、汇总进度。完整保存三次电话日志，不等于模型能稳定得出“已经达到最多三次”的结论。

状态栏由 Harness 提前计算并放在轨迹尾部，例如：

```xml
<agent_status>
- phone_call: Xfinity 3/3，已达到上限
- TODO: 取消套餐（进行中）
- working_directory: /workspace/project
</agent_status>
```

它可包含任务计划、工具调用计数、时间与位置等侧信道信息、工作目录、错误摘要和环境状态。状态栏紧邻下一次输出，模型无需再次遍历整个历史。

### （二）状态由谁创建、谁使用

1. Harness 监听用户消息、模型动作与工具结果。
2. 确定性代码更新计数器、TODO 和环境状态。
3. Harness 在调用模型前把摘要作为结构化消息放到轨迹末尾。
4. 模型读取状态并决策，但不负责把状态当作事实重新证明。

状态栏是原始轨迹的有损投影，只包含设计者预先选择的维度。若问题需要状态栏未记录的信息，仍必须保留或回查原始证据。

### （三）更新状态的两种方式

更新状态有两种实现方式，各有明确的缓存代价：

**实现一：每轮替换**。每次 API 调用前，从消息列表中移除上一轮的状态消息，在末尾追加最新状态。这保证了上下文中只有一份状态、永远是最新的。但代价是：移除旧状态会使其位置之后的所有缓存失效——这与本章批评的 “动态时间戳” 是同一个失效机制，区别只在于状态消息位于上下文末尾，失效范围只覆盖上次注入后新增的消息（通常是一轮），整个前缀仍可复用。

**实现二：持久追加**。状态消息一旦注入就永久留在轨迹中，每轮只在末尾追加新的状态。Claude Code 的 `<system-reminder>` 采用的就是这种方式——历史状态消息保留在会话记录（transcript）中，从不删改。这种方式对缓存完全友好：所有消息只追加、不修改，前缀始终稳定。代价是陈旧的状态会在上下文中累积，既占用 token，也要求模型自己关注 “最新一条” 状态而忽略已过时的旧状态。

取舍需要综合考虑轨迹长度、状态消息大小、两次更新间新增的后缀长度和预计更新次数。**状态很小、两次更新间产生的消息很多，且会话长度受控时，选择实现二**——保留旧状态通常比反复重算长后缀便宜；**状态较大、更新频繁或轨迹很长时，选择实现一**——它通常只使上次注入后的短后缀失效，同时避免陈旧状态持续累积。

状态小、更新间隔长、会话受控时可倾向追加；状态大、更新频繁、轨迹很长时可倾向替换。选择依据是缓存重算成本、额外 token 和陈旧状态歧义，而不是绝对规定。

## 八、上下文压缩：在保留证据边界的前提下做减法

### （一）为什么窗口没满也需要压缩

压缩有三种动机：避免超过长度与成本预算；把分散原始记录提炼成更容易检索的结论；缓解长任务接近窗口上限时可能出现的提前收尾倾向。

**上下文溢出**是装不下；**上下文腐化（Context Rot）**是仍装得下，但无关内容稀释注意力，使关键事实越来越难被稳定找到。二者不能混为一谈。

### （二）状态栏与压缩的关系

- 状态栏把提前计算的结论**添加**到历史末尾。
- 压缩把大段原始历史**替换**为精炼结论。
- 两者都在补足“模型易检索、难稳定归纳”的缺口，但状态栏更适合由代码维护的计数和状态，压缩更常用 LLM 对大段文本做语义蒸馏。

### （三）压缩与缓存如何取舍

压缩发生在两次模型调用之间，由 Harness 预处理消息历史。它通常会替换较早的工具结果，所以替换点之后的 Prompt Cache 会失效；但若不压缩导致窗口溢出，任务会直接失败。合理策略是接近阈值时批量压缩，而不是每轮零碎修改。

生产系统可分层处理：

1. 大型工具输出存外部介质，上下文只放稳定预览和引用。
2. 低价值噪声直接删除，不为噪声支付摘要成本。
3. 旧轨迹按轮次生成结构化归档，保留决策脉络。
4. 接近阈值时对未压缩内容批量做任务感知摘要。
5. 全量压缩作为最后手段，并设置失败熔断，防止反复压缩。

好摘要必须保留：关键决策、适用约束、失败路径、精确实体与时间，以及能回查原文的来源。压缩是有损的；带引用摘要相当于“有损内容 + 无损索引”，需要时可重新取证。

### （四）隔离优于事后压缩

如果某个探索任务会产生大量中间噪声，可交给独立子 Agent；主 Agent 只接收任务描述和结论摘要。这样原始搜索结果从未进入主上下文，不需要事后清理。

代价是子 Agent 看不到主 Agent 的全部历史，所以委派消息必须自包含：明确目标、范围、约束、期望证据和返回格式。隔离解决的是上下文污染，不等于自动保证结论正确，主 Agent 仍要审查关键证据。

## 九、完整机制

一个较完整的 Agent 每轮可以按以下顺序工作：

1. 开发者预先定义稳定系统指令、核心工具 schema、工具实现和 Skill 目录。
2. 用户提交任务，Harness 创建或读取会话轨迹。
3. Harness 根据任务加载必要 Skill；无关 Skill 正文不进入上下文。
4. Harness 用代码从轨迹和环境中派生 TODO、计数、目录等状态栏。
5. 若 token 接近预算，Harness 批量压缩较旧的工具结果，保留决策、约束、失败与来源。
6. Harness 构造“稳定前缀 + 动态轨迹 + 最新状态”，连同工具定义调用模型。
7. 模型返回文本或 `tool_calls`。文本可能结束本轮；工具请求则交还 Harness。
8. Harness 校验参数和权限，执行真实工具，把结果以 `tool_call_id` 关联后追加到轨迹。
9. 控制权回到第 4 步；状态更新、必要时压缩，再次调用模型。
10. 达到最终答案、明确失败、人工确认点或最大迭代次数时，Harness 停止循环。

其中缓存优化没有创造新业务能力，它降低的是重复处理稳定前缀的成本；提示工程规定长期规则；Skill 提供按需领域流程；状态栏提供当前显式状态；压缩与隔离控制历史噪声。这些组件最终都服务于同一目标：让模型在当前决策点看到“足够但不过量、可信且易用”的信息。
