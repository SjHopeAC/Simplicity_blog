# Task 2：Chapter 3 用户记忆和知识库（Memory 与 RAG）学习笔记

## 一、本章要解决的问题

第二章解决的是单次任务中“这一轮让模型看到什么”，第三章继续解决跨会话问题：对话结束后，哪些信息值得长期保存，后续任务如何准确取回，又怎样处理过期、冲突和隐私。

本章包含两条主线：

1. **用户记忆**：与特定 `user_id` 绑定，保存个人偏好、关系、历史事件和长期约束。
2. **知识库**：面向一组用户共享，保存法规、产品文档、组织流程和专业资料。

二者规模不同，但底层过程相同：原始信息经过提取和组织后进入持久化存储，当前任务再通过检索取回少量相关内容，放入模型上下文。

```text
原始对话或文档
  → 提取/清洗/分块
  → 建立索引并持久化
  → 根据当前问题检索
  → 重排序和证据核验
  → 注入当前上下文
  → 模型回答或继续检索
```

## 二、前置概念：轨迹、长期记忆与业务状态

### （一）三者分别保存什么

1. **轨迹（Trajectory）**：一次任务里的用户消息、模型动作和工具结果，按时间追加，主要服务当前会话、调试和审计。
2. **用户长期记忆（Long-term Memory）**：跨会话提炼出来的稳定信息，例如座位偏好、饮食限制、亲属关系和历史事件。
3. **业务状态（Business State）**：程序定义的任务阶段，例如“等待付款”“等待人工确认”“请求完成”。

轨迹是流水账，长期记忆是档案，业务状态是状态机。把三者混在一个消息列表里，会同时造成上下文膨胀、事实过期和状态判断不可靠。

> 原始轨迹可以只增不改，用于追溯证据；长期记忆允许合并、更新和淘汰；业务状态则必须遵守确定性的状态转换规则。

### （二）记忆设计的三个正交维度

| 维度     | 回答的问题 | 典型选择                                   |
| -------- | ---------- | ------------------------------------------ |
| 记忆层次 | 存在哪里   | 当前轨迹、长期记忆、业务状态               |
| 存储格式 | 怎么存     | Simple Notes、段落、JSON Cards、可执行对象 |
| 认知类型 | 存什么     | 情景记忆、语义记忆、程序记忆               |

**情景记忆**保存具体事件；**语义记忆**保存从事件中抽象出的稳定事实；**程序记忆**保存反复验证过的做事流程。同一条语义记忆既可以写成一句 Note，也可以写入结构化 JSON Card，这两套分类不能混为一谈。

## 三、用户记忆的写入、读取与更新

### （一）长期记忆接口的最小形态

用 `Protocol` 表示“任何记忆存储实现都要具备的行为”：

```python
from dataclasses import dataclass
from typing import Protocol

@dataclass
class MemoryRecord:
    memory_id: str
    user_id: str
    content: str
    source_id: str
    created_at: str

class MemoryStore(Protocol):
    def add(self, record: MemoryRecord) -> None: ...
    def search(self, user_id: str, query: str, top_k: int) -> list[MemoryRecord]: ...
    def delete(self, user_id: str, memory_id: str) -> None: ...

records = store.search(user_id="u-101", query="订机票偏好", top_k=5)
```

`MemoryStore` 是抽象接口，规定最小能力；`MemoryRecord` 是数据对象；具体实现可以使用 JSON 文件、关系数据库、向量数据库或混合索引。调用方依赖接口，不依赖底层存储。

### （二）记忆写入不是保存整段对话

一次会话结束后，后台记忆处理器读取新轨迹，由专门的提取模型生成候选记忆。候选结果至少要经过三项处理：

1. **选择**：短期工具输出和寒暄不进入长期记忆。
2. **抽象**：把“这次要求靠窗”归纳为“偏好靠窗座位”，但不能把一次偶然选择误判为永久偏好。
3. **结构化**：保存主体、关系、时间、来源和适用范围，避免同名实体混淆。

完整写入链如下：

```text
会话 Harness 保存原始轨迹
  → BackgroundMemoryProcessor 读取本轮新增消息
  → 提取模型生成候选事实
  → 核验来源、敏感性和置信度
  → 检索已有相似记忆
  → 执行 ADD / UPDATE / DELETE / NOOP 或仅追加
  → MemoryStore 持久化并更新索引
```

模型只提出候选事实和操作建议，真正的数据写入由记忆处理器调用 `MemoryStore` 完成。原始轨迹、候选记忆和最终记忆应保留关联 ID，便于回查来源。

### （三）四种存储格式

1. **Simple Notes**：每条只保存一个事实，成本低、更新简单，但多条信息间的关系容易丢失。
2. **Enhanced Notes**：用完整段落保留上下文，语义丰富，但冗余高且局部更新困难。
3. **JSON Cards**：按类别、子类别和键值组织，支持精确字段更新，但固定分类可能压扁多维信息。
4. **Advanced JSON Cards**：额外保存 `person`、`relationship`、`backstory`、时间和来源，适合人物消歧与跨会话关联，生成和维护成本最高。

实践中通常采用混合策略：少量关键身份、关系和约束使用 Advanced JSON Cards；大量低风险事实使用 Notes；完整原始对话放入可检索的历史库，不全部常驻上下文。

### （四）冲突更新的两种路线

**写入时消歧**会检索旧记忆，再让模型选择 `ADD/UPDATE/DELETE/NOOP`。优点是记忆库简洁；缺点是一次错误更新可能丢失历史。

**只追加写入、读取时判断**会保留带时间戳的多条事实，查询时融合语义、关键词、实体和时间信号。优点是历史可追溯；缺点是检索和排序更复杂。

无论采用哪条路线，都不能只覆盖旧值而不保留来源和时间，否则“以前住北京，后来搬到上海”会被压成一个无法解释的当前值。

## 四、记忆能力如何评估

### （一）三层评估框架

1. **基础回忆**：能否准确保存和返回用户直接给出的单条事实。
2. **多会话检索**：能否从不同时间、不同对象的会话中找全相关信息并完成消歧。
3. **主动服务**：能否发现多个记忆之间的隐藏关系，在风险发生前给出有证据的提醒。

例如“记住会员号”属于第一层；识别用户有两辆车并询问要预约哪辆属于第二层；订国际机票时主动发现护照临近过期属于第三层。

### （二）评估链路

```text
测试会话按时间依次输入
  → 被测系统只能根据已有记忆处理下一段会话
  → 完成全部会话后提出新问题
  → 系统根据记忆回答
  → 评估器对照参考答案、来源和遗漏项打分
```

`LLM-as-a-judge` 可以评价开放式答案，但不能成为唯一证据。精确字段应用确定性断言，检索系统应同时记录 Recall、Precision、MRR 或 NDCG，涉及主动服务时还要检查是否出现无依据的主动推断。

## 五、RAG：把外部知识放进当前上下文

### （一）RAG 是什么

RAG（Retrieval-Augmented Generation，检索增强生成）把知识存储和语言生成分开：检索器负责找证据，模型负责基于证据组织答案。它不会把整个知识库写入模型参数，也不会把所有文档一次塞进上下文。

```python
def answer(query: str) -> str:
    chunks = retriever.search(query, top_k=20)
    evidence = reranker.rerank(query, chunks)[:5]
    return llm.generate(question=query, context=evidence)
```

对象关系是：索引器创建文档块和索引；检索器持有或访问索引；重排序器读取候选结果；Harness 把最终证据放入上下文；模型只看到被选中的证据，不直接持有知识库。

### （二）索引阶段与查询阶段

```text
索引阶段：文档 → 清洗 → 分块 → 稀疏/稠密表示 → 索引
查询阶段：问题 → 多路召回 → 融合 → 重排序 → 证据注入 → 生成
```

索引阶段错误会污染后续全部查询；查询阶段则要在召回率、精度、延迟和 token 成本之间平衡。

## 六、分块、稀疏检索与稠密检索

### （一）文档分块

分块过大时，每个块包含太多无关内容，召回结果浪费上下文；分块过小时，代词、标题和因果关系被切断。常见策略包括固定长度、递归按标题/段落切分和按语义边界切分，并保留适量 overlap。

每个块至少应携带：`document_id`、章节路径、页码或行号、时间、访问权限和内容哈希。检索结果没有来源位置，就很难核验和更新。

### （二）稀疏检索：BM25

BM25 根据词项匹配、逆文档频率、词频饱和和文档长度归一化打分。它擅长代码、产品编号、人名和精确术语，但无法自然理解同义表达。

> 同一个词重复十次不会线性获得十倍分数；`k1` 控制词频饱和，`b` 控制文档长度归一化。

### （三）稠密检索：Embedding

Embedding 模型把文本映射为向量，查询与文档可以用余弦相似度等指标比较。它擅长语义相近但字面不同的表达，但可能漏掉罕见编号、拼写和精确实体。

向量数量较大时通常使用 ANN（Approximate Nearest Neighbor，近似最近邻）索引。HNSW 用多层图换取较高召回和较低查询延迟；Annoy 使用随机投影树，索引简单且适合只读场景。ANN 提高速度，但返回的是近似最近邻，不保证绝对精确。

### （四）混合检索与重排序

混合检索先分别取得 BM25 与向量候选，再融合结果。若两路分数尺度不一致，可使用 RRF（Reciprocal Rank Fusion，倒数排名融合）

RRF 依赖排名而不是原始分数，适合融合不同检索器。随后由 Cross-Encoder 或 LLM 重排序器同时读取“问题 + 候选块”，给出更精确的相关性排序。正确顺序是先用便宜检索扩大召回，再用昂贵模型缩小结果。

## 七、从扁平索引到结构化知识

### （一）RAPTOR 与 GraphRAG

**RAPTOR** 对文档块聚类并逐层生成摘要，形成从叶子细节到高层主题的树，适合“先找宏观概念，再下钻细节”。

**GraphRAG** 提取实体、关系和社区结构，适合回答“谁与谁有关”“A 如何影响 B”这类关系问题。它的成本在于实体消歧、图更新和关系质量控制。

两者不是更高级的普通向量库，而是改变了知识的组织方式。事实型短查询未必需要复杂结构；跨章节总结和多跳关系查询才更可能受益。

### （二）文件系统也可以是知识库

目录、文件名、标题和链接本身就是结构。Agent 可以先读索引和 README，再按需进入子目录，形成渐进式披露。文件系统可读、可编辑、可版本控制，但仍需要权限边界、命名规范和过期知识清理。

## 八、Agentic RAG：由模型控制检索循环

传统 RAG 通常只检索一次；Agentic RAG 把 `search_knowledge_base` 暴露为工具，让模型根据已有结果决定是否改写问题、继续搜索或停止。

```text
Harness 接收用户问题
  → 模型拆分信息需求
  → 调用 search(query_1)
  → 检索器返回带来源的证据
  → 模型判断缺口并调用 search(query_2)
  → 证据足够后综合回答
  → 验证器检查引用是否支撑结论
```

Agentic RAG 适合需要多跳取证、查询条件逐步明确的问题。单一事实查询采用固定检索管道更便宜、更稳定。模型每多一轮搜索都会增加延迟和费用，因此 Harness 需要限制查询轮数、去重相似查询并记录证据覆盖情况。

## 九、上下文感知检索

普通分块可能留下“该公司本季度增长 3%”这样的孤立句子，失去公司、年份和章节背景。上下文感知检索在**索引阶段**先为每个块生成简短背景前缀，再把“前缀 + 原块”建立稀疏和稠密索引。

```text
原块：本季度收入增长 3%
前缀：本段来自 ACME 公司 2025 年第二季度财报的关键业绩章节
索引内容：前缀 + 原块
```

它与第二章的上下文感知压缩不同：前者在索引期给知识块补背景，是加法；后者在运行期删除当前会话中的低价值历史，是减法。

代价是每个块需要额外模型调用，且错误前缀会污染检索。前缀生成必须保留原文、来源和模型版本，不能用生成摘要替代原始证据。

## 十、双层用户记忆架构

高质量用户记忆不能只靠“全部常驻”或“全部检索”。更稳妥的结构是：

```text
第一层：少量 Advanced JSON Cards
  → 保存身份、关键关系、长期偏好和高风险约束
  → 每轮可直接进入上下文，提供全局概览

第二层：上下文感知的原始对话索引
  → 保存大量历史细节和来源
  → 当前任务按需检索，提供精确证据
```

例如订国际机票时，模型先从常驻卡片看到“护照即将到期”和“准备去东京”，再调用记忆检索工具找回护照日期与机票时间的原始对话，确认后才给出续签提醒。

完整控制链是：

1. 会话 Harness 保存原始轨迹。
2. 后台处理器提取少量核心事实，更新 JSON Cards。
3. 索引器按会话或语义窗口切分原始历史，为每块补充人物、时间和事件背景。
4. 新任务开始时，Harness 先加载当前用户的核心卡片。
5. 模型发现需要历史细节时调用 `search_user_memory`。
6. 检索器执行混合召回与重排序，返回带来源的对话块。
7. 模型联合概览与细节推理，验证器检查结论是否有来源支撑。

## 十一、隐私、删除与知识更新

用户记忆通常包含 PII、凭证和行为偏好，写入前应完成敏感信息识别和分级。日志脱敏要保留可调试结构，但替换邮箱、手机号、令牌等真实值；密钥类信息原则上不应进入模型日志。

记忆系统还要支持：

- 按 `user_id` 隔离，禁止跨用户召回；
- 记录来源、时间、用途和保留期限；
- 用户可查看、更正和删除记忆；
- 删除原记录后同步清除派生索引和缓存；
- 文档更新时按 `document_id + hash` 增量重建受影响块；
- 定期合并重复项、标记冲突并淘汰过期内容。

> “数据库中删掉一行”不一定完成遗忘。向量索引、摘要、缓存、备份和评估日志中可能仍有派生副本，删除流程必须覆盖完整数据链。

## 十二、完整机制

一个带用户记忆与知识库的 Agent 可按下面的顺序工作：

1. 用户发起任务，Harness 根据 `user_id` 加载少量核心记忆。
2. 模型分析问题；需要共享知识时调用知识库检索，需要个人历史时调用用户记忆检索。
3. 检索层执行稀疏和稠密召回，融合、去重、重排序后返回带来源证据。
4. 模型根据证据回答；复杂问题可继续改写查询，但受轮数和费用限制。
5. Harness 或验证器检查引用、权限、时间有效性和冲突。
6. 会话结束后，原始轨迹先进入只增日志。
7. 后台处理器提取候选记忆，核验后更新核心卡片与历史索引。
8. 定期任务整理重复、冲突和过期知识，删除流程同步处理所有派生副本。

这套系统的关键不是“存得越多越好”，而是保留可追溯原始证据，只让当前任务需要的少量信息进入上下文，并让每次写入和读取都受到用户边界、时间与来源约束。
