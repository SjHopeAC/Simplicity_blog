# Task 3：Chapter 4 Tools 与 MCP 学习笔记

## 一、本章要解决的问题

模型只能生成 token，工具才让 Agent 获得观察环境、改变环境和驱动其他参与者的能力。本章主要解决四个问题：

1. 一项能力应该做成专用工具、通用执行器还是 Skill；
2. 工具如何描述，模型才能正确选择并传递参数；
3. MCP 如何统一 Agent 与外部工具、数据源之间的通信；
4. 工具从十几个增长到成百上千后，怎样按需发现而不塞满上下文。

工具是模型与环境之间的接口，不是模型本身。模型返回工具调用，只代表提出动作；真实副作用发生在 Harness、MCP 客户端或 MCP 服务器执行具体实现时。

## 二、工具的五种类型

| 类型         | 调用方向             | 主要作用          | 例子                       |
| ------------ | -------------------- | ----------------- | -------------------------- |
| 感知工具     | Agent 主动调用       | 获取信息          | 搜索、读文件、查询数据库   |
| 执行工具     | Agent 主动调用       | 改变环境          | 写文件、运行命令、发送邮件 |
| 协作工具     | Agent 主动调用       | 驱动 Agent 或人类 | 创建子 Agent、请求人工确认 |
| 用户沟通工具 | Agent 主动调用       | 向用户传递信息    | 回复、通知、结构化卡片     |
| 事件触发工具 | Agent 注册，外部触发 | 唤醒 Agent        | 定时器、Webhook、邮件事件  |

感知工具重点控制返回信息量；执行工具重点控制权限、副作用和验证；协作工具重点处理生命周期、上下文交接和超时；用户沟通与事件触发工具则依赖异步运行时。

> 设置定时器时，Agent 主动执行的是“注册”；到达时间后由外部事件触发运行。注册动作与真正唤醒 Agent 是两个时刻。

## 三、工具调用的语法、协议与真实执行

### （一）最小工具声明

```python
tools = [{
    "type": "function",
    "function": {
        "name": "read_document",
        "description": "读取已知路径的文档内容；不能搜索未知文件",
        "parameters": {
            "type": "object",
            "properties": {
                "path": {"type": "string"},
                "file_type": {
                    "type": "string",
                    "enum": ["pdf", "docx", "pptx"]
                }
            },
            "required": ["path", "file_type"]
        }
    }
}]
```

Python 语法上，`tools` 只是列表和字典；API 协议上，它是提供给模型的 JSON Schema；Agent 设计上，它描述动作名称、适用条件和参数边界。声明本身不会读取任何文件。

### （二）真实执行位置

```python
tool_registry = {"read_document": read_document}

call = response.choices[0].message.tool_calls[0]
arguments = json.loads(call.function.arguments)
result = tool_registry[call.function.name](**arguments)
```

`tool_registry` 持有“模型看到的名称 → 真实函数”的映射。真正副作用从最后一行开始；随后 Harness 还要把结果包装成带 `tool_call_id` 的 `tool` 消息，才能让模型在下一轮看到结果。

```text
Harness 提交工具 schema
  → Model 返回 tool_call
  → Harness 校验名称、参数和权限
  → 查找工具实现并执行
  → Environment 返回结果
  → Harness 追加 tool 消息
  → Model 根据结果继续决策
```

## 四、ACI：工具应围绕 Agent 的目标设计

ACI（Agent-Computer Interface）研究 Agent 怎样高效使用计算机，类似 HCI 研究人怎样使用计算机。它强调工具应对应 Agent 的目标，而不是机械包装每个底层 API。

例如文档读取不一定要拆成 `extract_pdf_text`、`extract_docx_content` 和 `extract_pptx_content`，可以合并成统一的 `read_document(path, file_type)`。这样模型只需学习“读取文档”这一概念，新增格式也不会增加工具选择负担。

工具粒度的判断标准是功能相似性和使用场景重叠度：

- 过细：工具数量多，模型容易选错；
- 过粗：参数结构复杂，错误定位困难；
- 合理：一个目标对应一个清晰动作，并能返回可验证结果。

## 五、专用工具、通用执行器与 Skill

### （一）三种能力表达方式

1. **专用工具**：结构化函数调用，schema 明确，可做权限和审计，适合高风险或复杂参数。
2. **通用执行器**：如 Shell、Code Interpreter，模型通过代码组合能力，覆盖范围大。
3. **Skill**：自然语言流程文档，告诉 Agent 按什么步骤使用已有工具，适合频繁变化的操作知识。

例如“部署应用”可以做成 `deploy_app` 专用工具，也可以由 Skill 指导 Agent 依次运行构建、打包和部署命令。

### （二）默认选择与例外

普通、低风险、可在沙盒内完成的任务优先使用通用执行器，因为一段 Python 或 Shell 能覆盖大量预先无法枚举的需求。以下情况更适合专用工具：

1. 涉及生产写操作、支付或审计，需要精细权限；
2. 参数为复杂嵌套对象，需要 schema 强约束；
3. 操作频率极高，需要稳定入口；
4. 需要屏蔽 Windows、macOS、Linux 或供应商差异。

Skill 适合变更频繁、参数较简单、主要由流程知识驱动的能力。复杂参数通过命令行传递时容易出现引号和转义错误，可让 Skill 先把结构化参数写入 JSON 文件，再由命令读取。

### （三）形态与披露是两个问题

“做成工具还是 Skill”决定每项能力怎样表达；“一次让模型看到多少项能力”决定披露策略。一个 MCP 服务器可以有几百个专用工具但只暴露索引，一个 Skill 目录也可能多到需要检索。不能因为采用 Skill 就认为工具规模问题自动消失。

## 六、工具描述与参数保真

### （一）描述重点是何时用、何时不用

工具描述至少包含：

- 适用条件；
- 不适用边界；
- 参数格式与具体例子；
- 返回值结构；
- 失败语义和调用代价；
- 与相似工具的区别。

“搜索相关内容”只描述功能；“需要实时信息或未知外部事实时使用，不用于搜索本地文件”才能指导模型决策。时间戳、手机号等参数应同时给出格式和样例，避免模型在复杂任务中额外推断。

### （二）参数保真

工具层不能静默修改模型输入，例如把中文弯引号自动替换为直引号，或私自给 Git 命令追加参数。否则模型看到的世界与工具实际操作的世界不一致，会出现无法诊断的重复失败。

确实需要规范化时，必须同时满足：

1. 在工具描述中声明转换规则；
2. 在返回值中告知转换后的真实参数；
3. 日志保留原始值和执行值；
4. 不改变参数的业务含义。

## 七、MCP 的角色与三类原语

### （一）MCP 解决什么问题

不同 Agent 框架原本各有一套工具格式。MCP（Model Context Protocol）通过统一协议，使同一个外部能力能被不同客户端接入。

MCP 采用客户端—服务器结构：

- **MCP Host**：承载 Agent 的应用，例如 IDE 或桌面客户端；负责权限、上下文和用户交互。
- **MCP Client**：Host 内的协议客户端，与某一个 MCP Server 建立会话。
- **MCP Server**：暴露工具、资源和提示模板，执行自己的业务逻辑。
- **Environment**：Server 最终访问的文件、数据库、网页或外部服务。

Host 创建和持有 Client；Client 负责协议通信；Server 持有工具实现或资源适配器；Model 不直接建立 MCP 连接。

### （二）工具、资源与提示模板

1. **Tools**：模型可以请求执行的动作，例如查询天气、写入工单。
2. **Resources**：应用可浏览和读取的只读数据，例如文件内容、数据库记录。
3. **Prompts**：服务器提供的可复用提示模板，由客户端或用户选择。

三者分别对应“可执行动作”“可读取数据”“可选流程模板”。资源读取不等同于工具执行，提示模板也不会自动产生副作用。

### （三）本地与远程传输

本地 MCP Server 通常作为子进程运行，通过 `stdio` 通信；远程 Server 通常通过 Streamable HTTP 通信。传输层只解决消息怎样到达，不决定哪些工具应该暴露给模型，也不替 Host 完成权限审批。

### （四）MCP 工具调用链

```text
Host 启动或连接 MCP Server
  → MCP Client 初始化会话
  → Client 请求 tools/list
  → Server 返回工具名称、描述和参数 schema
  → Host 选择性地把工具定义交给 Model
  → Model 返回工具调用请求
  → Host 做权限和参数检查
  → Client 发送 tools/call
  → Server 执行工具并访问 Environment
  → Server 返回结构化结果
  → Host 把结果写入 Agent 轨迹
```

`tools/list` 返回完整工具清单，不代表 Host 必须把全部 schema 塞进每次模型请求。工具发现与上下文披露属于 Host/Harness 的责任。

## 八、MCP 与 Skill Hub 的安全边界

第三方 MCP Server 和 Skill 都会扩大信任边界：前者可能运行第三方程序、接收凭证并返回不可信数据；后者可能把不可信指令和脚本带入本地环境。

主要风险包括：

1. **工具描述投毒**：恶意指令藏在 `description` 中进入模型上下文；
2. **供应链攻击**：服务器或 Skill 后续更新引入恶意行为；
3. **工具遮蔽**：恶意 Server 注册同名工具，截获敏感参数；
4. **权限过大**：多个 Server 共用高权限凭证；
5. **本地代码执行**：带脚本 Skill 或本地 MCP Server 以用户权限运行。

接入时应审查描述和代码、锁定版本、使用最小权限凭证、隔离文件与网络范围，并为高风险动作增加独立审批。安全扫描只能降低风险，不能代替运行时权限控制。

## 九、工具过多时的渐进式披露

### （一）按需加载

启动时只给模型工具名称、简短描述或分组索引；模型确定需要某项能力后，再读取完整 schema。这样可以降低 token 占用，并让稳定前缀继续命中 Prompt Cache。

常见分组包括搜索、读取、解析和结构化查询。分组目录用于缩小选择范围，完整工具定义仍按需加载。

### （二）主动工具发现

主动发现不是根据用户第一句话一次性选工具，而是让 Agent 在执行过程中发现能力缺口：

```text
静态前缀只包含基础工具 + discover_tools
  → Agent 发现“需要查询股票价格的能力”
  → 调用 discover_tools(自然语言需求)
  → 检索器先匹配服务器，再匹配具体工具
  → 返回少量候选及完整 schema
  → Harness 将 schema 追加到轨迹
  → Agent 调用新工具
```

两级匹配先找 MCP Server，再在 Server 内找工具，能减少跨领域混淆。若相似度低于阈值，应明确返回未找到，让 Agent 改写需求、使用基础工具实现或停止，而不是硬塞一个不相关工具。

新 schema 应固定在首次注入的轨迹位置，不要每轮重排工具集；否则会从变动点开始破坏缓存。

## 十、感知工具

感知工具的返回值会进入模型上下文，因此重点是结果粒度、分页、截断和来源。搜索工具应返回标题、URL、摘要与时间；读文件工具应支持范围读取；大结果应保存到外部文件，只把头尾和定位信息放入上下文。

多模态信息有三种处理路线：

1. **原生多模态**：模型直接读取图像、音频或 PDF，保真度高，token 和模型成本较高。
2. **提取为文本**：先 OCR 或 ASR，再交给语言模型，适合文本占主导的内容，但丢失版式和视觉关系。
3. **工具化分析**：主模型调用 `analyze_image` 等工具，由专门多模态模型回答具体问题，成本和灵活性较平衡。

选择标准是任务是否依赖视觉布局、原始多模态 token 成本以及是否需要反复追问。

## 十一、执行工具的安全与验证

### （一）多层防护

执行工具应按顺序经过：

```text
Schema 校验
  → 路径/命令/API 输入检查
  → 权限与工作区边界
  → 风险分类
  → 必要时独立审批或人工确认
  → 沙盒执行
  → 自动验证
  → 结构化结果与审计日志
```

发现异常输入时应快速拒绝，不能偷偷“智能修正”。黑名单只能作为基础层，不能独立承担安全保证。

### （二）提议者—审核者与 Sidecar

**提议者—审核者**适合审批高风险方案或在执行后检查产物；开放式审查需要能力相近但偏好不同的独立模型，并引入测试、截图或外部事实等新证据。

**Sidecar**是伴随主循环运行的轻量审查器，主要判断某一次结构化工具调用是否安全。它只读取工具名、参数和权限上下文，不读取可能被提示注入污染的自由文本理由。连续拒绝应触发熔断并转交用户，不能无限重试。

### （三）执行—验证—反馈闭环

文件写入后自动运行 linter，代码修改后执行测试，配置更新后在沙盒启动验证。工具不应只返回“成功”，而应返回可检查的结果：退出码、错误位置、测试统计和产物路径。

长输出只将必要头尾送入上下文，完整结果保存到文件并返回引用。Python `venv` 只隔离依赖，不是安全沙盒；不可信代码应使用容器或 microVM，并限制 CPU、内存、磁盘、网络和运行时间。

### （四）幂等性与取消

超时不代表副作用一定没有发生。可重试操作应携带幂等键，服务端对重复请求返回第一次结果；或在重试前查询目标状态。发送邮件、拨打电话、转账等不可逆操作不能盲目重试，应采用“预检—确认—执行”并保存外部回执。

## 十二、协作工具

协作工具可归纳为三组原语：

1. **启动与取消**：`spawn_subagent`、`cancel_subagent`；
2. **消息与状态**：发送补充指令、查询结果、报告进度；
3. **发现**：列出 Agent 的职责和运行状态。

子 Agent 应获得自包含任务：目标、范围、约束、可用证据、输出格式和停止条件。主 Agent 创建子 Agent，子 Agent 持有独立上下文并调用自己的工具；完成后返回结构化摘要或产物引用，而不是把全部轨迹塞回主上下文。

HITL（Human-In-The-Loop）用于不可逆、价值判断或信息不足的节点。请求人工输入需要超时、默认保守行为、优先级和通知渠道；批准或拒绝理由还可以成为后续评估与改进数据。
