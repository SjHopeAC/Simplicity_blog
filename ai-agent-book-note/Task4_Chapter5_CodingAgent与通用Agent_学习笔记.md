# Task 4：Chapter 5 Coding Agent 与通用 Agent 学习笔记

## 一、本章要解决的问题

开放任务型通用 Agent 的任务边界和产物形态无法提前穷举，因此不能为每个需求预先开发专用工具。

Coding Agent 不只是“会写程序的聊天模型”。它能够读取环境、修改文件、执行代码、观察反馈并继续修正。代码在这里是一种元能力：可以完成计算、表达规则、转换数据、生成文档和界面，也能临时创造新工具。

这一判断有适用边界。开放式调研、内容生成和数据处理适合以 Coding 为核心；任务空间封闭的客服、审批等系统仍应以固定流程和专用业务工具为主，Coding 只承担计算和校验。

## 二、前置概念：代码、Artifact 与 Harness

### （一）代码为什么是元能力

自然语言规则可能含糊，代码必须明确输入、条件和输出；代码执行还能产生客观反馈。因此代码同时具备两种价值：

1. **思考介质**：把数学、逻辑和业务条件转换成可执行形式；
2. **交付介质**：生成 PDF、PPT、图表、网页、SQL、视频或新 Agent。

### （二）Artifact 是什么

Artifact 是 Agent 生成、可由其他系统直接消费的独立产物，例如脚本、SQL、HTML、图表和配置文件。LLM 只负责生成 Artifact，不必把大量数据读进上下文后再复述。

例如 ERP 查询可让模型生成只读 SQL，由数据库执行后直接把结果交给前端表格。数据路径是“数据库 → 前端”，不是“数据库 → LLM → 自然语言 → 用户”。

### （三）Harness 提供什么

Harness 负责上下文、工具、约束、验证与纠正。在 Coding 场景中对应：

- 项目指令和文件上下文；
- 读、搜、编辑、终端等工具；
- 工作区与权限边界；
- Linter、类型检查、测试和 CI；
- Git、沙盒、快照和失败恢复。

代码任务之所以适合 Agent，不只是模型会写代码，更因为软件工程已经具备大量自动验证基础设施。

## 三、Coding Agent 的七个基础工具

1. **Code Interpreter**：在隔离环境执行 Python，适合计算和数据处理。
2. **Bash Shell**：执行构建、测试和项目命令。
3. **Read**：读取已知文件或指定范围。
4. **Write**：创建文件或完整重写。
5. **Edit/Patch**：对现有文件做局部修改。
6. **Glob**：按文件名模式定位文件，例如 `**/*.py`。
7. **Grep**：在文件内容中检索符号或文本。

这七个工具主要覆盖第四章的感知与执行两类。单个 Shell 已能完成多数动作，但单独的 Read、Grep 和 Patch 可以提供更清晰的行号、结构化反馈和跨平台一致性，也更容易实施权限控制。

## 四、最小 Coding Agent 循环

### （一）核心接口

工具注册表负责把模型的工具名映射为真实实现：

```python
class ToolRegistry:
    def __init__(self) -> None:
        self._tools: dict[str, callable] = {}

    def register(self, name: str, fn: callable) -> None:
        self._tools[name] = fn

    def execute(self, name: str, arguments: dict):
        return self._tools[name](**arguments)

registry = ToolRegistry()
registry.register("read_file", read_file)
registry.register("apply_patch", apply_patch)
registry.register("run_command", run_command)
```

`ToolRegistry` 由 Harness 创建并持有；工具函数访问工作区；模型只产生名称和参数，不持有 Python 函数对象。

### （二）读—搜—改—测—修

```python
for step in range(max_steps):
    response = model(messages=messages, tools=tool_schemas)
    messages.append(response)

    if not response.tool_calls:
        if acceptance_passed():
            return response.content
        messages.append(feedback("验收未通过，继续修复"))
        continue

    for call in response.tool_calls:
        result = registry.execute(call.name, call.arguments)
        messages.append(tool_result(call.id, result))

raise RuntimeError("达到最大步骤数")
```

关键点是 `not response.tool_calls` 不能直接等于任务完成。模型停止调用工具，只说明它准备输出文本；最终是否完成应由测试、验收脚本或人工确认决定。

### （三）完整控制链

```text
用户提交任务
  → Harness 读取项目指令与工作区状态
  → Model 选择 Glob/Grep/Read 调研
  → Harness 执行只读工具并返回结果
  → Model 生成 Patch
  → Harness 检查路径与补丁后写入文件
  → Model 调用测试或构建命令
  → Environment 返回退出码和错误
  → Model 根据反馈继续修复
  → 验收器通过后 Harness 才允许结束
```

## 五、项目理解与项目指令文件

Coding Agent 首次进入仓库时，应先确认项目结构、构建系统、主要模块、调用方和测试入口。缺少上下文时直接修改，容易只修表象或破坏其他路径。

`AGENTS.md`、`CLAUDE.md`、`.cursorrules` 等项目指令文件相当于项目级系统提示词，适合保存：

- 正确的构建和测试命令；
- 代码风格和架构约束；
- 禁止修改的目录；
- 提交与验收要求；
- 项目特有的常见陷阱。

它们由 Harness 在会话开始时加载，属于稳定前缀。README 面向开发者介绍项目，项目指令文件则直接约束 Agent 的工作方式。

## 六、从需求到交付的工程流程

### （一）需求理解与范围判断

简单、边界清晰的修改可以直接进入实现；复杂任务应先确认目标、影响范围、可接受权衡和完成标准。例如“优化性能”必须先确定是延迟、吞吐量还是内存问题，并找到当前瓶颈。

### （二）设计文档

复杂任务的设计文档应说明修改模块、调用关系、方案取舍、新依赖、兼容性和验证计划。设计审查发生在大量代码产生前，是成本较低的人类介入点。

### （三）实现与测试

实现阶段优先复用已有抽象并控制 diff。验证至少包含正常路径、边界条件和异常路径。测试失败后，Agent 应根据错误定位并修复，不能只把失败转述给用户。

### （四）代码审查与文档同步

测试通过后仍要检查可读性、安全、性能和架构一致性。架构、接口或依赖发生变化时应同步更新文档；过时文档会直接误导后续 Agent。

> 这是一套按风险裁剪的流程，不是每个小修复都必须写长设计文档。任务越复杂、影响越广、结果越难回滚，需要的前置设计和人工审查越多。

## 七、Harness 工程：完成必须由证据判定

### （一）任务的四种状态

| 目标 | 自动验证 | 结果                                   |
| ---- | -------- | -------------------------------------- |
| 明确 | 有       | 最适合 Agent，例如修复带失败测试的 Bug |
| 明确 | 无       | 依赖人工审查，吞吐受人限制             |
| 模糊 | 有       | 会高效地跑偏                           |
| 模糊 | 无       | 难以可靠启动                           |

Harness 的目标是把任务推向“目标明确 + 自动验证”：把验收标准写成测试、类型检查、静态规则或可查询状态。

### （二）测试不是唯一验证

不同产物需要不同证据：

- 代码：单元测试、集成测试、类型检查、Linter；
- 网页：启动服务、浏览器交互、截图和可访问性检查；
- PPT/PDF：渲染后检查页面、文字截断和图表；
- 数据库：查询真实状态和事务结果；
- 外部系统：保存服务端回执和幂等键。

模型自己说“已完成”不属于验证证据。

## 八、文件搜索与编辑工具

### （一）搜索顺序

常见调研顺序是：

```text
Glob 确认目录与候选文件
  → Grep 定位符号、调用方和测试
  → Read 读取必要上下文
  → 修改前再次确认当前文件内容
```

搜索应优先使用符号名、错误信息和调用点，不必从仓库根目录逐个文件读取。只读调研和写入阶段要区分，避免还没理解就改动。

### （二）局部补丁优于整文件重写

Patch 应包含明确的上下文和最小修改范围。工具必须在原文本不匹配时失败，不能模糊猜测后静默修改。写入后应重新读取受影响片段，并运行最相关的验证。

同时存在用户未提交修改时，Agent 不能覆盖、回退或格式化无关文件。Git 回滚只处理本次明确创建的改动，不能把整个工作区恢复到 HEAD。

## 九、故障与错误恢复

### （一）错误分类

1. **模型错误**：选错文件、误解需求、生成错误代码；
2. **工具错误**：参数非法、权限不足、超时或工具实现故障；
3. **环境错误**：依赖缺失、网络失败、服务不可用；
4. **验证错误**：测试不稳定、验收器本身有缺陷；
5. **协议错误**：厂商不接受另一模型的思考块或工具格式。

错误分类决定恢复动作。权限不足应请求授权，依赖缺失应报告环境问题，测试失败才进入代码修复；不能把所有失败都当成“再问模型一次”。

### （二）最大循环与回退

Harness 应限制步骤数、连续相同错误次数、时间和费用。重复失败达到阈值后，应保存当前证据并停止或转交人工。Git、沙盒和快照提供回退能力，但回退目标必须精确。

### （三）跨厂商轨迹接管

不同供应商的思考块、签名和工具消息格式并不兼容。跨厂商切换时应使用中立轨迹：保留用户消息、可公开的模型文本、工具调用和结果，去除供应商私有元数据；必要时生成带来源的状态摘要。

流式输出中断也不能一律整轮重发。正文可在已确认前缀后续写；工具参数若在 JSON 中间断裂，直接拼接可能得到“语法合法但业务错误”的参数，应重新生成完整调用并使用幂等机制防止重复副作用。

## 十、Coding Agent 的安全边界

### （一）致命三要素

当系统同时具备“不可信输入、敏感数据访问、对外通信”时，提示注入可能把敏感数据发送出去。安全设计应尽量打断其中至少一项：隔离外部内容、限制凭证和文件范围、控制网络出口，并在高风险外发前确认。

### （二）沙盒与最小权限

本地虚拟环境不等于沙盒。执行不可信代码时应使用受限工作区、容器或 microVM，限制网络、CPU、内存和时间。默认只读或 workspace-write，高风险命令和工作区外访问单独审批。

### （三）动态生成软件的权限下沉

应用代码由 Agent 动态生成时，不能把最终权限边界也交给它。租户隔离、字段约束、合法状态转换和访问身份应由稳定的数据层强制执行。应用层可做预检查改善体验，数据层保留最终裁决权。

## 十一、代码可以作为思考工具

### （一）数学

模型把计算步骤转换为 Python、SymPy 或数值程序，执行后读取精确结果。代码能减少心算错误，但前提是模型正确建模；程序跑通不代表数学含义一定正确。

### （二）逻辑与约束求解

自然语言条件可转换为 CSP、SAT 或 SMT 约束：

```python
problem.addConstraint(lambda age, verified: age >= 18 and verified)
solutions = problem.getSolutions()
```

约束求解器保证对已编码规则进行一致搜索，但翻译遗漏条件会得到稳定的错误答案。因此要分别验证“自然语言 → 约束”的忠实度和“求解器执行”的正确性。

### （三）业务规则代码化

复杂政策可以写成服务端确定性函数，让模型负责提取事实和解释结果，代码负责最终判定。规则版本、输入字段和输出理由必须可审计；模型不能覆盖代码的拒绝结果。

## 十二、代码作为内容和系统适配器

### （一）多媒体生成

PPT、视频和 CAD 可以通过代码生成，再由独立 Reviewer 查看渲染结果。有效循环是：

```text
Proposer 生成代码
  → 运行代码产生可见产物
  → Reviewer 读取截图、音频或尺寸测量
  → 返回结构化缺陷
  → Proposer 定向修复
```

Reviewer 的价值来自新证据，不是把同一段代码再读一次。规则明确、尺寸精确、需要可编辑时优先代码路线；自然形态和开放式视觉创作更适合生成模型。

### （二）自适应系统

日志格式变化时，Agent 可以分析失败样本、生成新的解析函数、自动生成测试，通过后再热加载。生成逻辑进入生产前必须经过隔离测试、版本记录和回滚门禁。

### （三）生成式 UI

Agent 可以生成 HTML 表单一次收集多个澄清项，也能修改 React 代码后通过 HMR 即时展示。但直接执行任意 HTML/JavaScript 有注入风险；标准表单和卡片可使用声明式组件协议，只允许选择受信任组件。

### （四）Artifact 数据路径

SQL、可视化和转换脚本应作为 Artifact 交给专门执行层。SQL 使用只读账号、参数绑定、表白名单、超时和行数限制；可视化代码在隔离环境运行。Artifact 缩短数据路径，但不替代权限检查。

## 十三、Agent 自举

Coding Agent 可以生成新 Agent，但不应完全从空白开始。更可靠的方式是复制经过验证的 Agent 模板，再修改系统提示词、工具和业务逻辑，同时保留消息结构、工具循环、安全门和测试。

自我修复同样采用“确定性检查优先，LLM 处理长尾”的结构：过期锁文件和配置格式由规则检查；规则无法覆盖的日志因果分析再交给模型。
