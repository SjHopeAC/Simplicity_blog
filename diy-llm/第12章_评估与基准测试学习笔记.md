# 第 12 章：评估与基准测试学习笔记

> 依据 Datawhale 的[《Diy-LLM》第 12 章：评估与基准测试](https://datawhalechina.github.io/diy-llm/chapter12/chapter12_%E8%AF%84%E4%BC%B0%E4%B8%8E%E5%9F%BA%E5%87%86%E6%B5%8B%E8%AF%95.html)整理。

评估看起来是在给模型打分，实际上是在回答：“这个模型对某个具体目标来说，到底好不好？”如果目标不同，评估方法也会不同，所以不存在一个能概括全部能力的分数。

---

## 12.1 常见的评估信号

最常见的是 Benchmark，也就是让多个模型完成同一套标准题目，再比较准确率或其他指标。例如 MMLU、GPQA、MATH、SWE-Bench 等分别关注知识、推理、数学或代码能力。

除了标准基准，还可以看：

- 人类盲测偏好；
- 真实用户使用量和留存；
- 社区中的实际使用反馈；
- 推理延迟、吞吐量和成本；
- 安全性与拒答表现。

这些信号各自只能反映一部分能力。标准题方便比较，却可能离真实使用很远；用户投票更接近实际感受，却容易受回答长度、表达风格和用户构成影响。

**Tip:** 排行榜会随着模型版本、测试规则和时间变化。记录结果时最好同时保存模型版本、评测日期、提示模板和工具使用条件。

---

## 12.2 如何设计一次评估

课程把评估拆成四个问题。

### 12.2.1 输入是什么

先确定测试问题从哪里来，以及是否覆盖目标场景。客服模型应该测试真实客服问题，代码模型则要测试真实仓库中的修改任务，而不是只做通用选择题。

评估集还要包含少见但重要的长尾情况，例如歧义输入、复杂任务、罕见领域和对抗性问题。

### 12.2.2 如何调用模型

调用方式会明显改变结果，需要说明：

- zero-shot 还是 few-shot；
- 是否允许思维链；
- temperature 等采样参数；
- 是否可以使用搜索、RAG、代码解释器等工具；
- 测试的是裸模型，还是包含 Agent 框架的完整系统。

同一个模型加上检索和工具后，系统能力可能大幅提高，但这时评估对象已经不只是模型参数本身。

### 12.2.3 如何评价输出

有标准答案的任务可以自动计算准确率、F1 或代码测试通过率。开放问题没有唯一答案，可以使用人工评估、LLM-as-a-judge、用户反馈或 A/B 测试。

评价时还要考虑错误代价。在医疗、法律等场景中，一次自信的错误可能比一次谨慎拒答严重得多。

### 12.2.4 如何解读结果

一个模型得到 90 分，并不自动表示它能安全部署。还要问：

- 测试题是否代表真实任务；
- 分数差异是否稳定；
- 测试数据是否被模型见过；
- 提升是否值得额外的延迟和费用；
- 比较的是方法、模型，还是完整产品系统。

个人扩展：自己做项目时，可以先写“失败标准”，例如回答事实错误、工具参数错误或超过 3 秒都算失败。先规定规则再测试，比看完结果后临时调整标准更可信。

## 12.3 困惑度（Perplexity）

困惑度衡量模型对一段文本的预测有多确定。可以把它理解为：模型在预测下一个 token 时，平均面对多少个差不多可能的选择。

```text
困惑度越低 → 模型越能预测这类文本
```

它一般由平均交叉熵取指数得到：

```text
PPL = exp(平均 token 损失)
```

训练集困惑度低只能说明模型拟合了训练数据。要观察泛化能力，必须在没有参与训练的验证集或测试集上计算。

困惑度的优点是变化连续、容易跟踪，也不需要为每个文本额外标注答案，因此适合观察预训练进度和 Scaling Law。

它的局限也很明显：

- 困惑度低不等于事实一定正确；
- 它不能直接代表指令遵循、安全和工具使用能力；
- 黑盒 API 通常不会提供完整 token 概率；
- 测试语料分布会影响结果。

**Tip:** 使用不同 tokenizer 的模型，其 token 划分和序列长度不同，困惑度通常不能直接横向比较。最好使用一致的数据、分词方式和计算口径。

课程还介绍了 LAMBADA 完形填空和 HellaSwag 常识推理。它们把语言建模能力放进更具体的上下文任务中，比只看整段文本的困惑度更容易解释。

## 12.4 知识类基准

知识类基准主要测试模型掌握事实和专业知识的程度。

- MMLU：覆盖数学、历史、法律等多个学科的选择题；
- MMLU-Pro：清理部分简单或有噪声的问题，并增加选项数量；
- GPQA：由专业人员设计的高难度研究生级问题；
- Humanity's Last Exam：覆盖多学科、多模态的高难度题目。

这类基准方便量化，但容易遇到两个问题：题库泄漏进训练数据，以及高分只代表“会考试”，不一定代表能完成真实工作。

---

## 12.5 指令遵循基准

这类评估关注模型能否按照用户要求回答。

### Chatbot Arena

把两个匿名模型的回答同时给用户，由用户选择更好的一个。优点是输入来自真实用户、模型可以持续加入；缺点是投票人群不固定，也容易偏爱较长、更有风格的回答。

### IFEval

使用可以自动检查的要求，例如“必须包含五句话”或“不能出现某个词”。它很适合测试格式约束，但遵守格式不代表内容质量高。

### AlpacaEval 与 WildBench

它们通常让另一个强模型担任裁判，可以低成本评价开放式回答。风险是裁判模型可能有长度偏好、自我偏好或固定风格偏好。

**Tip:** 使用 LLM-as-a-judge 时，最好打乱候选答案顺序、控制长度影响，并抽取一部分结果由人复核。

## 12.6 智能体基准

智能体基准不只测试一次回答，而是让模型在环境中规划、调用工具并根据结果继续行动。

- SWE-Bench：根据真实 GitHub issue 修改代码，并运行测试验证；
- CyBench：完成网络安全 CTF 任务；
- MLE-Bench：完成数据处理、训练和调参等机器学习竞赛流程。

这种评估更接近实际工作，但结果同时受模型、提示词、工具、环境和 Agent 框架影响。失败可能不是模型不会推理，而是工具调用格式错误、环境依赖缺失或没有正确恢复状态。

个人扩展：评估 Agent 时不要只记录最终成功率，还应记录工具调用成功率、平均步骤数、错误恢复率、耗时和费用。这样才知道失败发生在哪一层。

## 12.7 纯推理基准

ARC-AGI 使用输入和输出网格，让模型从少量示例中推断变换规则，再应用到新网格。它尽量减少语言知识的影响，关注抽象模式识别和泛化。

但“纯推理”也很难完全定义。模型是否见过相似题型、是否允许写程序搜索、给多少计算预算，都会影响结果。

---

## 12.8 安全基准

安全评估关注模型是否会协助完成有害行为，以及模型是否会被越狱提示绕过。

- HarmBench：覆盖多类有害行为并检查模型响应；
- AIR-Bench：按照风险类别和政策框架构建评测；
- 越狱测试：尝试使用特殊提示绕过拒答规则。

安全不能只看拒答率。模型如果对正常问题也大量拒答，虽然“更保守”，却不一定更有用。还要分别衡量有害请求拒绝、正常请求通过、事实可靠性和高风险能力。

---

## 12.9 真实性

许多公开基准像考试题，而真实用户更多是在求助，例如修改文件、总结材料或解决工作问题。

更真实的评估应尽量接近实际输入分布。课程提到 Clio 用隐私保护方式分析真实用户需求，MedHELM 则由临床人员提供真实医疗任务。

真实性和可公开性之间存在冲突：越接近真实业务，越可能包含隐私、内部流程和不能公开的数据。

---

## 12.10 有效性

### 训练集与测试集重叠

大模型在互联网规模的数据上训练，公开测试题很可能已经出现在训练数据里。此时高分可能来自记忆，而不是泛化。

可以通过去重、构建较新的私有测试集、检查异常高概率样本和报告数据重叠情况来降低风险，但很难完全消除。

### 数据集质量

测试集本身也可能存在错误答案、描述不清和标注不一致。如果题目有问题，再精确的评分程序也会得到错误结论。

因此，测试集也需要版本管理、人工抽查和争议样本处理流程。

---

## 12.11 我们到底在评估什么

过去常在固定训练集和规则下比较一种算法是否更好，这更像在评估“方法”。现在的大模型评测经常允许使用不同数据、工具和后训练流程，更像在比较最终“模型或系统”。

两种比较都合理，但不能混在一起：

- 研究新算法时，应尽量控制其他变量；
- 为业务选择模型时，更应该比较端到端效果、成本和稳定性。

一次比较是否可信，首先取决于评估对象和规则有没有说明白，而不是表格里的数字有多少位小数。
